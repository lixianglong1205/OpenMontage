# 脚本导演 - Screen Demo 流水线

## 何时使用

你要把已检视的录屏转成带时间戳的程序化脚本。与讲解类内容不同，你不是在发明流程，而是在让语言与观众将亲眼看到的操作同步。

## 前提条件

| 层级 | 资源 | 用途 |
|-------|----------|---------|
| Schema | `schemas/artifacts/script.schema.json` | 产物校验 |
| 前置产物 | `state.artifacts["idea"]["brief"]` | 含工作流、关键瞬间与来源说明的 brief |
| 工具 | `transcriber`, `frame_sampler`, `audio_enhance` | 音频/转录检视与抽检 |

## 流程

### 1. 确定脚本模式

根据 brief 元数据在三种模式中选一种：

| 旁白状态 | 策略 |
|-----------------|----------|
| `voiced` | 转录、收紧表述，并在可行处保留说话人的措辞 |
| `silent` | 围绕操作撰写以文字为主或可选 TTS 就绪的旁白 |
| `partial` | 转录已有语音，仅在必要处做衔接 |

若录屏无声且 preflight 中 TTS 不可用，不要假设之后会有旁白。脚本应仍能通过字幕、钩子卡片与步骤标签让成片成立。

### 2. 构建操作映射

操作映射是本阶段真正的骨架。将 `frame_sampler` 与 `transcriber` 配合使用，记录：

- 精确的任务边界，
- 值得高亮的点击，
- 值得放慢的输入，
- 值得加速或剪掉的无意义等待，
- 应以实时保留的结果瞬间。

将详细操作信息存入 `script.metadata.interaction_map`。保持 `sections` 简洁且符合 schema。

`interaction_map` 常用字段：

- `timestamp_seconds`
- `action_type`
- `target`
- `importance`
- `suggested_treatment`（`realtime`, `speed_up`, `cut`, `highlight`, `zoom`）

### 3. 按步骤撰写章节

每个 `script.sections[]` 应对应真实的用户步骤，而非主题性段落。

合适的章节标签示例：

- `打开设置面板`
- `粘贴 API token`
- `运行构建`
- `验证实时结果`

每个章节应完成三件事：

- 说明正在发生什么，
- 说明为何重要，
- 为高光、缩放或变速留下清晰提示。

### 4. 保持旁白程序化

遵循经研究验证的规则：

- 叙述意图与效果，而非显而易见的鼠标移动，
- 措辞简短直接，
- 除非目标受众明显需要，否则避免行话，
- 让屏幕上的动作与措辞同步，
- 若源素材已有旁白，保留说话人的自然语气。

### 5. 标注节奏决策

在章节级备注与 `metadata.speed_plan` 中标注：

| 速度系数 | 何时使用 | 示例 |
|-------------|-------------|---------|
| `0.75-1.0x` | 重要点击或结果 | 小控件、关键验证瞬间 |
| `1.5-2.0x` | 常规输入或导航 | 填写明显字段 |
| `3.0-6.0x` | 安装、构建、加载 | 依赖安装、编译 |
| `cut` | 无学习价值 | 长时间空等 |

不要把关键证明瞬间放在加速段落里。

### 6. 用元数据承载屏幕相关细节

推荐的 `script.metadata` 字段：

- `interaction_map`
- `speed_plan`
- `chapter_candidates`
- `pronunciation_guides`
- `callout_candidates`
- `sections_needing_zoom`

### 7. 质量门禁

| 标准 | 问题 |
|-----------|----------|
| **操作覆盖** | brief 中的每个关键瞬间是否都标注了时间戳？ |
| **旁白同步** | 每段旁白是否与屏幕上的动作一致？ |
| **变速标注** | 无效时段是否标记为加速或删除？ |
| **增强密度** | 高光是否只用于真正的注意力转移，而非每次点击？ |
| **技术准确** | 软件名、命令与 UI 元素是否命名正确？ |
| **用词经济** | 旁白是否简洁且程序化？ |

### 制作过程中的事实核验

若在撰写脚本时遇到不确定之处：
- 使用 `web_search` 在写入脚本前核验事实性陈述
- 使用 `web_search` 查找参考图以保证视觉准确
- 在决策日志中记录：`category="visual_accuracy_check"`

脚本中的每条事实性陈述应可追溯到 `research_brief`。
若你做出 research 中未出现的陈述，需补充调研并添加来源。不要编造统计、日期或归属。

## 常见陷阱

- 旁白描述光标而非结果。
- 让口播节奏偏离画面动作。
- 以实时保留构建与加载画面。
- 为无声录屏写暗中依赖不可用 TTS 的脚本。
