# 脚本导演 — 动画流水线

## 何时使用

本阶段将已批准的提案转化为适合动画制作的节拍。脚本必须为动作、场面调度与停留时间留出空间，并整合调研结论、遵循所选动画模式。

## 前提条件

| 层级 | 资源 | 用途 |
|-------|----------|---------|
| Schema | `schemas/artifacts/script.schema.json` | 产物校验 |
| 前置产物 | Proposal Director 的 `proposal_packet` | 选定概念、动画模式、目标时长、复用策略 |
| 可选产物 | Research Director 的 `research_brief` | 数据点、受众洞察、准确性约束 |
| 元技能 | `skills/meta/voice-performance-director.md` | 结构化 TTS 表达提示，用于自然、有表现力的旁白 |
| 工具 | `transcriber` | 可选的源稿转写支持 |

## 流程

### 1. 吸收提案

通读 `proposal_packet.selected_concept`。提取：

- **标题与钩子** — 开场必须兑现这一承诺
- **动画模式** — `manim`、`remotion`、`ai_video`、`diagram_stills` 或 `mixed`。这会约束你的写作方式。
- **叙事结构** — `progressive_build`、`myth_busting`、`journey` 等。按结构来写。
- **目标时长** — 字数预算 = target_seconds × 2.5 词/秒（按 150 WPM）
- **要点** — 来自 `selected_concept.key_points`
- **复用策略** — 重复出现的母题意味着重复的脚本结构

若存在 `research_brief`，还需提取：
- **数据点** — 将具体、有来源的事实织入旁白（避免空泛断言）
- **受众误解** — 在脚本中直接回应
- **数学准确性说明** — 哪些可以简化、哪些不能

### 2. 按动画节拍写作

每个段落应表达**一个**清晰的视觉想法：

- **Statement（陈述）** — 引入概念（入场动画）
- **Demonstration（演示）** — 展示其如何运作（主动画）
- **Transformation（变换）** — 从一种状态过渡到另一种（转场）
- **Comparison（对比）** — 并排或顺序展示两件事（分屏或顺序）
- **Conclusion（结论）** — 落定洞察（停留 + 强调）

若以旁白为主导，还需按 `skills/meta/voice-performance-director.md` 创建 `voice_performance` 与各段的 `delivery_cues`。动作密集的视频需要旁白上的「呼吸空间」：在观众必须消化动画处标记停顿，在揭示、变换或对比落地处标记强调。

**动画模式影响写作风格：**

| 模式 | 写作风格 |
|------|---------------|
| Manim | 精确、数学化。每个节拍对应具体几何变换。旁白描述屏幕上正在展示的内容。 |
| Remotion | 数据驱动、节奏明快。每个节拍对应图表/组件动画。旁白补充视觉数据。 |
| AI Video | 描述性、富有画面感。每个节拍描述 AI 应生成的场景。旁白补充视觉无法传达的语境。 |
| Diagram Stills | 解释性、渐进式。每个节拍为构建中的示意图增加一层。旁白逐步讲解构建过程。 |
| Mixed | 各段不同 — 在元数据中标注每段的模式。 |

### 3. 屏幕文字保持精简

动画比重高的作品，若画面运动时观众需阅读过多文字，容易失败：

- 屏幕标题 **最多 8 个词**
- 屏幕说明 **最多 15 个词**
- 优先短语而非完整句
- 优先数字与标签而非段落
- 数学记号可以保留 — 在数学动画模式中它本身就是内容

### 4. 为视觉停留留出空间

不要每秒都塞入新信息。场景规划需要时间为：

- **Entrances（入场）**（0.5–1s）：对象出现在屏幕上
- **Reveals（揭示）**（1–2s）：逐步展现复杂度
- **Holds（停留）**（1–3s）：让观众消化所见
- **Exits（退场）**（0.5s）：清空舞台以进入下一节拍

**经验法则：** 每 10 秒旁白，预留 3–4 秒视觉「呼吸」时间。90 秒视频约应有 60–65 秒旁白与约 25–30 秒视觉停留。

### 5. 用元数据表达动作意图

建议每段使用的元数据键：

- `beat_type`：statement / demonstration / transformation / comparison / conclusion
- `animation_mode`：本段使用的模式（mixed 模式尤其重要）
- `text_constraints`：本段屏幕文字最大词数
- `narration_plan`：旁白与视觉的关系（描述 / 补充 / 静默）
- `visual_priority`：观众应聚焦之处（动画、文字、数据）
- `hold_time_seconds`：本段内容之后的最小视觉停留时间
- `delivery_cues`：语速、能量、强调、停顿时机，以及供 TTS 使用的旁白文本
- `data_source`：若本段使用调研数据点，在此引用

### 6. 调研整合

若存在 `research_brief`：

- 旁白中至少使用 2 个来自调研的数据点
- 用调研中最令人意外的发现支撑钩子
- 若叙事结构支持，至少回应 1 个受众误解
- 自然引用来源（「According to [source]...」或「A [year] study found...」）
- **不要**编造统计数据 — 仅使用调研已发现的内容

### 7. 质量门

提交脚本前确认：

- [ ] 每段支撑**一个**强视觉想法
- [ ] 屏幕文字简洁（短语，非段落）
- [ ] 节奏对动画友好（已预算停留时间）
- [ ] 旁白主导的段落包含具体的 `delivery_cues` 与 `voice_performance` 示例段
- [ ] 字数在目标时长的 ±10% 以内
- [ ] 写作风格符合动画模式
- [ ] 已整合调研数据点（若有 research_brief）
- [ ] 保持数学准确性（若适用）
- [ ] 后续阶段能从此脚本清晰映射场景

### 制作过程中的事实核查

若在写脚本时遇到不确定之处：
- 使用 `web_search` 在写入脚本前核实事实性陈述
- 使用 `web_search` 查找参考图以保证视觉准确
- 在决策日志中记录：`category="visual_accuracy_check"`

脚本中的每条事实性陈述应可追溯到 `research_brief`。
若提出调研中未包含的断言，需补充调研并添加来源。**不要**编造统计、日期或归因。

## 常见陷阱

- **一段塞入过多想法。** 一个节拍 = 一个视觉想法。
- **把字幕与屏幕文字混为一谈。** 字幕是旁白的转写。屏幕文字是动画设计的一部分。
- **忘记动作需要停顿与强调。** 预算停留时间。
- **忽略动画模式。** Manim 脚本与 AI 视频脚本的写法不同。
- **存在 research_brief 却写无调研支撑的脚本。** 若调研有惊人数据，要用上。泛泛脚本浪费调研投入。
- **过度简化数学以致错误。** 查阅 research brief 中的准确性说明。
