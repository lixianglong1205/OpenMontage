# Pull Request 审查指南

本指南面向社区审查者、维护者与审查 OpenMontage 拉取请求的 AI 助手。这是一套审查框架，而非封闭清单。用它组织审查过程，并继续发现与当前 PR 相关的具体问题。

OpenMontage 是 agent 编排的视频生产系统。许多 PR 的影响不止于所改文件：提供商变更可能影响工具发现、选择器路由、设置说明、流水线决策、成本报告以及用户可见的生产流程。好的审查能保护这些契约。

## 审查心态

从这些问题入手：

- 此 PR 是否推动 OpenMontage 朝正确方向前进？
- 范围是否聚焦，还是混入了无关变更？
- 合并后，用户、维护者或 agent 能否理解行为？
- PR 是否保持 agent 优先架构？
- 是否会在提供商发现、流水线产物或渲染行为上引入回归？
- 测试与文档是否与行为变更处于同一层级地更新？
- 是否存在安全、隐私、依赖或供应链方面的顾虑？

答案可以是「有用，但尚不可合并」。当方向对齐但实现需清理时，这是合理的审查结果。

## 审查产出

有用的审查通常应得出以下之一：

- **Approve（批准）**：PR 有用、聚焦、经测试且风险足够低可合并。
- **Comment（评论）**：PR 有前景，但批准前需清理。
- **Request changes（请求修改）**：PR 存在会引入回归、破坏契约或误导用户的阻塞项。
- **Close or redirect（关闭或重定向）**：PR 方向不对、多为噪音，或应先开 issue/讨论再写代码。

避免橡皮图章式批准。也避免把每个顾虑都升格为阻塞项。说明实际严重程度并解释影响。

## 通用审查领域

### 项目方向

检查 PR 是否解决真实的 OpenMontage 问题。

- 是否提升视频生产质量、可靠性、速度、可移植性、提供商覆盖、本地执行、文档、测试或贡献者体验？
- 是否重复现有路径而未改进？
- 是否为无明确用户工作流的推测性功能？
- 是否引入与价值不成比例的维护负担？

### 范围卫生

噪音会使审查不安全。

- 是否改动了无关文件？
- lockfile 是否仅在依赖实际变更时才改？
- 是否无理由包含生成文件、截图、二进制资产或本地产物？
- 文档/测试修复是否与功能工作捆绑从而掩盖风险？
- 分支相对最新 `main` 是否已过时？

若 PR 有用但嘈杂，在深入批准前要求收窄 diff。

### 回归风险

不要只看变更文件。

- 变更影响现有用户还是仅新增可选路径？
- 是否改变默认提供商选择、回退行为或设置菜单？
- 是否改变 schema、产物或流水线阶段契约？
- 是否改变渲染输出、时序、音频、字幕或文件路径？
- 是否在本应告知用户处产生静默回退？

### 安全与供应链

用事实与证据审查安全问题。不要公开断言贡献者意图。若见可疑代码，描述行为与风险。

检查：

- 新的网络调用、上传、遥测或后台进程
- 密钥外泄风险、读取 `.env`、记录 token 或不安全的调试输出
- Shell 执行、`subprocess`、动态 import、`eval`、`exec` 或生成代码执行
- 依赖新增、安装脚本、package-lock 变动或宽泛版本范围
- 不安全的文件删除、路径遍历、解压或写入预期项目目录之外
- 未在元数据中体现的远程模型下载或提供商调用
- 外部内容可能指示 agent 的提示注入面

使用如下表述：

- 「我发现安全阻塞项：该命令执行用户可控输入。」
- 「合并前需说明此依赖变更的理由。」
- 「在已审查的 diff 中未发现可行动的安全问题。」

避免公开表述如：

- 「无恶意意图。」
- 「此作者安全。」
- 「这肯定无害。」

### 性能与资源使用

OpenMontage 涉及视频、音频、图像生成与本地模型。小改动可能带来巨大运行时成本。

- PR 是否重复加载模型而非复用状态？
- 是否下载大文件却缺少清晰的设置/状态信息？
- 是否增加渲染时间、内存、VRAM、磁盘或网络使用？
- 是否以可能拖慢常见路径的方式改变抽帧、合成、编码或音频处理？
- 资源画像与成本估算是否切合实际？

## OpenMontage 架构检查

### Agent 优先架构

OpenMontage 的控制面是 agent 遵循 markdown 技能与 YAML 清单。Python 应提供工具与持久化，而非隐藏编排。

标记以下 PR：

- 为创意决策、阶段转换或审查策略增加 Python 编排器
- 在代码中隐藏提供商/模型/运行时决策且无用户可见性
- 绕过流水线清单、阶段 director 技能、检查点或审查
- 将质量策略移入临时代码而非文档化说明

好的 PR 将智能保留在说明与契约中，Python 处理边界清晰的执行。

### 工具契约

每个工具应继承 `tools/base_tool.py` 并满足 `BaseTool` 契约。

对新改工具审查：

- `name`、`version`、`tier`、`capability`、`provider`
- `runtime`、`stability`、`execution_mode`、`determinism`
- 使用 `cmd:`、`env:`、`python:` 等支持前缀的 `dependencies`
- `install_instructions`
- `input_schema`、`output_schema` 与产物行为
- `supports`、`best_for`、`not_good_for`
- `resource_profile`
- `retry_policy`
- `fallback` 与 `fallback_tools`
- `agent_skills`
- `user_visible_verification`
- 相关处的 `estimate_cost()` 与 `estimate_runtime()`
- `execute()` 返回 `ToolResult`

元数据面向用户。若设置、离线行为、成本、模型下载或硬件要求不准确，提供商菜单与 agent 规划会误导用户。

### 工具注册表与发现

工具发现经 `tools/tool_registry.py`。除非有充分理由，避免硬编码工具列表。

检查：

- 工具是否通过常规包发现注册？
- 是否使用正确 `capability` 以便选择器能找到？
- `get_status()` 是否准确报告可用性？
- 某一可选提供商的 import 失败是否会破坏无关发现？
- 提供商菜单是否展示有用的设置说明？
- PR 是否意外让不可用工具看起来已配置？

有用命令：

```bash
python -c "from tools.tool_registry import registry; import json; registry.discover(); print(json.dumps(registry.capability_catalog(), indent=2))"
python -c "from tools.tool_registry import registry; import json; registry.discover(); print(json.dumps(registry.provider_menu_summary(), indent=2))"
```

### 选择器与提供商

选择器将能力级请求路由到提供商工具：

- `tts_selector`
- `image_selector`
- `video_selector`

审查选择器或提供商变更时：

- 确认提供商具有正确 `capability`。
- 确认选择器输入名映射到提供商输入名。
- 确认提供商特定选项不会被静默忽略。
- 在显式指定时确认尊重用户偏好。
- 确认不可用提供商不会阻塞可用替代。
- 确认排序/回退变更有测试。
- 确认选择器仍返回有用的替代与理由。

新增提供商通常不应要求改选择器代码。若需要，PR 应说明原因。

### 流水线清单与阶段技能

流水线清单位于 `pipeline_defs/`。阶段说明位于 `skills/pipelines/`。

对流水线变更检查：

- 清单 schema 有效性
- 阶段顺序与阶段名
- `produces` 产物
- `tools_available`
- `review_focus`
- `success_criteria`
- `checkpoint_required`
- `human_approval_default`
- 匹配的 stage director 技能
- `tests/contracts/` 或 `tests/pipelines/` 中的测试

清单与阶段技能必须一致。若清单称某阶段产出 `scene_plan`，director 技能应实际指导创建有效的 `scene_plan`。

### 规范产物与 Schema

`schemas/artifacts/` 中的产物是阶段间契约。

审查 schema 或产物变更时：

- 每个生产者是否仍写出有效产物？
- 每个消费者是否仍理解该产物？
- 必填字段是否有理由？
- 是否需要迁移或向后兼容？
- 测试是否覆盖有效与无效示例？
- 检查点协议是否仍与变更后的产物配合？

Schema 变更是高影响项。除非 PR 能证明否则，应视为跨流水线变更。

### 检查点与审查策略

OpenMontage 用检查点实现恢复、人工批准、审计轨迹与阶段门控。

检查：

- PR 是否保留检查点状态语义？
- 是否避免跳过必需的人工批准？
- 是否在预期处保留成本快照与审查元数据？
- 是否避免将不完整的规范产物写成已完成阶段？
- 是否与 `skills/meta/checkpoint-protocol.md` 一致？
- 是否与 `skills/meta/reviewer.md` 一致？

审查逻辑应保持说明驱动，除非 PR 仅增加窄范围的机械式校验器。

### 合成运行时

OpenMontage 可用 Remotion、HyperFrames 或 FFmpeg 合成。运行时选择是用户可见的生产决策。

对渲染/合成 PR 检查：

- `video_compose` 是否保留显式 `render_runtime` 路由？
- 在相关处是否考虑 Remotion、HyperFrames 与 FFmpeg 路径？
- PR 是否避免静默运行时替换？
- 运行时不可用错误是否作为阻塞项明确暴露？
- Node、FFmpeg、`npx` 与包要求是否准确检查？
- 渲染报告是否含足够证据以调试失败？
- 当生产渲染路径不同时，浏览器预览是否视为 QA/调试产物？

从 motion-led 生产静默降级到 still-led 回退是审查发现项，而非无害实现细节。

### 成本、预算与付费提供商

OpenMontage 不应静默花钱或暗示付费提供商免费。

检查：

- 工具估算成本是否足够准确以用于规划？
- 首次使用付费提供商是否对用户可见？
- 提供商文档是否提及定价/免费层注意事项？
- 从付费到免费或从免费到付费的回退是否需要用户可见？
- 模型下载、托管端点或云 GPU 使用是否如实描述？

### 文档与用户可见声明

文档是产品的一部分。提供商设置文档常驱动 agent 行为。

检查：

- 新增提供商时 PR 是否更新 `docs/PROVIDERS.md`？
- 架构变更时 `docs/ARCHITECTURE.md` 是否需要更新？
- 在声称处，macOS、Windows、Linux 的设置说明是否准确？
- 文档是否区分 API 密钥、本地安装、模型下载与缓存离线运行？
- 包版本与模型版本是否清晰分离？
- 限制是否清楚说明？

## 场景特定审查提示

### 新提供商或工具

问：

- 此提供商对 OpenMontage 工作流是否有用？
- 是增加真实覆盖还是仅重复现有提供商？
- 提供商是否国际知名、在国家/区域重要，或对 OpenMontage 用户明显有价值？
- 工具是否可通过注册表发现？
- 匹配的选择器是否发现并路由到它？
- 提供商输入是否与选择器输入兼容？
- 状态检查是否反映真实可用性？
- 设置文档、依赖、成本、网络与缓存行为是否准确？
- 是否有聚焦测试？
- 是否避免在模块 import 时 import 重量级依赖？
- 生成产物是否写入预期路径？

最低预期覆盖：

- 工具元数据/契约测试
- 注册表发现测试
- 在需要时对依赖 mock 的状态行为测试
- 若加入选择器支持的能力，则选择器/路由测试
- 对用户可见提供商的文档更新

提供商可行性重要。OpenMontage 不应变成无人维护或一次性集成的杂物袋。提供商不必全球主导，但应有明确理由留在此项目中。

考虑：

- 是否有活跃用户群、维护中的 API 文档、SDK 支持或社区采用的证据？
- 是否国际广泛使用，或在特定国家、区域、语言或行业市场有意义地流行？
- 是否解锁现有提供商覆盖不佳的能力、语言、价格点、区域、质量档、合规姿态或本地/离线工作流？
- 定价、配额、API 访问、模型可用性与条款是否足够清晰供贡献者测试与维护集成？
- 提供商在未来六个月内是否可能仍可用？
- 提供商价值是否值得其增加的维护负担？

### 选择器变更

问：

- 是否仍自动发现提供商？
- 是否避免硬编码提供商列表？
- 是否保留显式用户偏好？
- 是否干净处理不可用提供商？
- 是否解释所选提供商？
- 是否保留考虑过的替代？
- 是否将共享输入映射到提供商特定输入？

### 本地 GPU 或模型运行时变更

问：

- 硬件要求是否准确？
- CPU/MPS/CUDA 行为是否与实现一致？
- 各设备的 dtype 选择是否安全？
- 模型下载与缓存行为是否有文档？
- 资源画像是否反映符合实际的 RAM、VRAM 与磁盘需求？
- 设置是否避免把本地 GPU 安装伪装成一分钟 API 密钥搞定？

### 渲染运行时变更

问：

- 是否保留 `edit_decisions.render_runtime` 中的运行时选择？
- 是否避免未经用户可见批准的回退？
- Remotion 与 HyperFrames 契约是否被尊重？
- 是否包含 smoke 测试或渲染探测？
- 是否在相关处用 ffprobe/帧/音频检查验证最终输出？

### 流水线或技能变更

问：

- 清单是否仍能通过校验？
- 阶段技能是否存在且与阶段名匹配？
- `review_focus` 与 `success_criteria` 是否有意义？
- 规范产物是否有效？
- 人工批准门控是否正确？
- 测试是否更新？

### Schema 变更

问：

- 哪些生产者与消费者受影响？
- 字段必填还是可选？
- 现有检查点/产物是否仍工作？
- 有效与无效数据是否更新测试？
- 变更是否需要迁移说明？

### 依赖或 Lockfile 变更

问：

- 依赖对 PR 是否必要？
- lockfile 变更是否成比例？
- 安装脚本或传递依赖是否有风险？
- 包是否维护中且许可合适？
- 是否在支持的 Python/Node 版本上工作？
- 版本边界是否过松或过紧？

### 仅文档变更

问：

- 文档技术上是否准确？
- 是否与当前代码与注册表行为一致？
- 是否过度承诺提供商质量、成本、离线运行或平台支持？
- 是否指向正确的设置与排障路径？

仅文档 PR 仍可能通过教错用户或 agent 而引入回归。

## 测试预期

按风险选测试。不要对每个小文档修复都要求昂贵集成测试，但对变更行为要有证据。

常见检查：

```bash
python -m pytest tests/contracts -q
python -m pytest tests/tools -q
python -m pytest tests/qa -q
python -m py_compile path/to/changed_file.py
```

对提供商 PR，聚焦的 mock 测试常优于昂贵 live API 测试。在凭证与成本可接受时 live 提供商 QA 有用，但契约不应依赖维护者配置每个提供商。

若无法运行测试，审查应说明原因及剩余风险。

## PR 评论指南

好的审查评论具体、基于证据且可行动。

优先：

- 「当前分支下此测试失败：`...`」
- 「此提供商不会被发现，因为 `capability` 设为 `...`。」
- 「此设置声明误导，因为首次运行会下载模型权重。」
- 「请将 lockfile 变动与此提供商变更拆分。」

避免：

- 模糊评论如「清理一下」
- 关于贡献者的个人评论
- 公开猜测意图
- 过度声称安全
- 存在明确阻塞项时冗长 nit 列表

当 PR 有多处问题时，优先一条合并评论，便于作者一次修完。对需要代码上下文的精确行级 bug 使用行内评论。

安全审查建议公开用语：

- 「我在此 diff 中发现可行动的安全问题。」
- 「合并前此区域需安全审查。」
- 「在已审查的 diff 中未发现可行动的安全问题。」

不要陈述或暗示贡献者有无恶意意图。审查代码与行为。

## 维护者与 AI Agent 工作流

本节公开以便贡献者理解审查如何执行。这是工作流，不限制审查者判断。

完整审查：

1. 拉取最新 `main`。
2. 在干净 worktree 中 checkout PR。
3. 查看 PR 元数据：标题、关联 issue、变更文件、作者说明与先前评论。
4. 审查 diff 的范围、有用性与架构契合度。
5. 识别 PR 场景：提供商、选择器、流水线、schema、运行时、文档、测试、依赖或混合。
6. 应用本指南中相关场景提示。
7. 运行聚焦测试或说明未运行原因。
8. 对照实现检查文档与用户可见声明。
9. 检查安全、依赖与供应链风险。
10. 按严重程度排序写出发现。
11. 决定：批准、评论、请求修改或关闭/重定向。

AI 辅助审查时，要求 agent 报告证据而非仅结论：

- 运行的命令及结果
- 检查的文件
- 触及的架构契约
- 仍未验证的风险
- 确切的合并阻塞项

不要仅凭摘要批准。审查者或 agent 应检查 diff 与相关项目契约。

## 合并就绪评分标准

批准前确认：

- PR 有用且与项目方向一致。
- diff 聚焦且无无关变动。
- 架构契约被保留。
- 测试在合适层级覆盖行为。
- 文档与用户可见行为一致。
- 已考虑安全与供应链风险。
- 性能、成本与资源声明切合实际。
- 分支足够新，审查发现仍有效。
- 剩余风险可接受且已说明。

批准不意味着 PR 完美。意味着变更有用、被理解、经适当测试且足够安全可落地。
